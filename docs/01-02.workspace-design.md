# Cargo Workspace 初始化設計

日期：2026-09-24  
範圍：workspace 設計與最小 skeleton；不實作 framework API。

## 1. 範圍與需求理解

此文件只決定最小 Cargo workspace 與 package 邊界，供後續 framework 開發使用。原始需求的核心是 compile-time dependency graph 與 runtime framework configuration 分離（[01-01.raw-framework-requirement.md，第 3–27 行](01-01.raw-framework-requirement.md#L3-L27)）；DI graph 預計在編譯期建立，並主要由 procedural macro 產生 wiring code（[第 100–119 行](01-01.raw-framework-requirement.md#L100-L119)）。

Common application template 會被 application 引用，application entry 負責收集 providers/hooks 並產生 wiring（[第 938–1,002 行](01-01.raw-framework-requirement.md#L938-L1002)）。因此 workspace 需要分開承載一般 Rust framework library 與 procedural macro library。

依使用者補充，未來 example guide 是獨立 consumer package，只依賴 `framework` facade，展示外部使用方式；framework 自身另有測試。現在不建立 guide package，也不讓 guide 直接依賴 `framework-macros`。

初始化前 repo 沒有 `Cargo.toml`、Rust source 或其他 Cargo package；Git index 只有 `.gitignore`，需求文件是 `docs/01-01.raw-framework-requirement.md`。`.gitignore` 第 3 行為 `tmp*`；新增 `/target/` 時保留該規則。此文件編號遵循 [AGENTS.md 第 3–5 行](../AGENTS.md#L3-L5) 的 `xx-yy.name` 規則。

## 2. Workspace 與 package 邊界

使用 virtual workspace root，不在根目錄放 library package：

```text
framework-rust/
├── Cargo.toml                    # virtual workspace
├── Cargo.lock
├── rust-toolchain.toml
├── crates/
│   ├── framework/
│   │   ├── Cargo.toml
│   │   └── src/lib.rs
│   └── framework-macros/
│       ├── Cargo.toml
│       └── src/lib.rs
├── docs/
└── .gitignore
```

| Package | 類型與責任 | 依賴方向 |
| --- | --- | --- |
| `framework` | 一般 library；承載未來 runtime framework 公開介面，並作為 consumer 匯入的 facade | 後續提供 macro re-export |
| `framework-macros` | `proc-macro` library；未來解析使用者提供的 Rust syntax 並產生 Rust code | 不依賴 `framework`，避免循環依賴 |

Procedural macro 必須位於 `proc-macro` crate，而且不能在定義它的 crate 內使用；這是 Rust 對 crate 邊界的要求，不是單純的目錄偏好。[Rust Reference：Procedural Macros](https://doc.rust-lang.org/reference/procedural-macros.html) 另外，這類 crate 只能匯出 procedural macros，不能同時作為一般 runtime library 匯出 framework traits。[Rust Reference：Linkage](https://doc.rust-lang.org/reference/linkage.html)

因此本設計依 raw requirement 明訂的 proc-macro 方案選擇兩個 package；這是 package 邊界決策，不代表現在定義或實作任何 macro API。需求文件把 provider declaration syntax 與 capability metadata 列為待設計事項（[第 1,452–1,487 行](01-01.raw-framework-requirement.md#L1452-L1487)）。

Package 名稱 `framework`、`framework-macros` 是設計階段的工作名稱；若將來發布到 crates.io，應在發布前確認名稱可用並定稿。現在不新增第三個 graph/core package：依賴 graph 的內部資料結構尚未設計；若未來有獨立重用或測試邊界，再評估抽出 package。

### 編譯與依賴資料流

```text
未來的 application / example guide package
              │ 僅依賴並匯入 framework facade
              ▼
          framework facade ──────► framework-macros（編譯器 host）
              ▲                            │
              └──── macro expansion 產生 Rust code
                           │
                           ▼
              application 連同 framework API 編譯至 target
```

`framework-macros` 在編譯期間讀取輸入語法並輸出 Rust tokens；展開後的程式碼使用 framework 公開介面。macro package 不需要依賴 framework package。workspace skeleton 預先建立 `framework` 對 macros package 的依賴，待 macro API 實作時再由 facade re-export；目前不匯出不存在的 macro。此階段不決定展開路徑、metadata 格式、圖演算法或公開 API。

## 3. Proc-macro package 是否現在需要

**需要納入 workspace，但只建立 package 邊界，不實作 macros。** 理由是 compile-time DI 和 procedural macro code generation 是原始需求已明訂的主要方案（[第 100–119 行](01-01.raw-framework-requirement.md#L100-L119)），而 Rust 規定 procedural macro 必須在獨立的 proc-macro crate 定義。若只初始化一般 library，之後加入該需求時必須再拆 package 並調整 facade 邊界。

目前不建立 `framework-graph`、guide 或測試 package。跨 crate provider metadata 與 capability discovery 是開始 macro 功能開發前必須通過的設計 gate：原始需求指出 proc macro 無法反射 trait implementation，且要求 compile-time discoverability（[第 1,148–1,195 行](01-01.raw-framework-requirement.md#L1148-L1195)）。本階段不設計其格式或傳遞機制；先以後續設計解決，再開始 macro 功能實作。實際 macro syntax 也仍待設計（[第 1,452–1,487 行](01-01.raw-framework-requirement.md#L1452-L1487)）。

## 4. Rust toolchain、edition 與版本政策

- **開發 toolchain：** 使用 `rust-toolchain.toml` 的 `channel = "stable"`，並安裝 `rustfmt`、`clippy`；不 pin 某個 patch release。
- **Edition：** workspace package 共用 `edition = "2024"`。截至 2026-09-24，官方 release list 的最新 stable 為 1.98.1（2026-09-03）；Rust 2024 自 1.85 穩定，因此這個 edition 本身要求至少 Rust 1.85，但不等於本專案宣告 MSRV。[Rust Release Announcements](https://blog.rust-lang.org/releases/)；[Rust 1.85 release](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)
- **MSRV：** 初始化不設定 `rust-version`，不承諾舊 compiler 支援範圍。待公開 API、依賴版本與 CI 矩陣定稿後，再決定並宣告 MSRV。
- **LTS 說明：** Cargo Rust Version 手冊指出，Rust Project 只為最新版本提供 bug fix 與 security update；LTS 討論仍是 pre-RFC，並記載目前不新增 rustup channel。因此本專案開發使用 stable，不宣稱自行提供 LTS 支援。[Cargo Rust Version](https://doc.rust-lang.org/cargo/reference/rust-version.html)；[Rust Internals：pre-RFC LTS](https://internals.rust-lang.org/t/pre-rfc-lts-for-the-rust-toolchain/24476)
- **Cargo resolver：** virtual workspace 設 `resolver = "3"`，與 Rust 2024 edition 的預設 resolver 一致；Cargo 文件說明 workspace root 可集中設定 resolver、共用 package metadata 與 lockfile。[Cargo Book：Workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html)；[Cargo Book：Dependency Resolution](https://doc.rust-lang.org/cargo/reference/resolver.html)
- **Target 平台：** 目前需求沒有 OS、embedded、`no_std` 或 wasm 要求，也沒有 platform-specific framework API。初始化先維持一般 `std` library，不加 target-specific dependency 或 CI target matrix。procedural macro 於 compiler host 執行，展開後的 framework/application 程式碼才編譯到 consumer target；若未來要求特定 target，再用實際 consumer case 驗證。

## 5. 初始化時的最小檔案

| 檔案 | 用途 |
| --- | --- |
| `Cargo.toml` | virtual workspace；列出上述兩個 members，設 `resolver = "3"`，集中 package version 與 edition |
| `Cargo.lock` | 由 Cargo 產生並納入 repo，固定 workspace 開發與 CI 使用的依賴解析結果 |
| `rust-toolchain.toml` | 選擇 stable channel、`rustfmt` 和 `clippy` |
| `.gitignore` | 保留現有 `tmp*`，新增 `/target/` |
| `crates/framework/Cargo.toml` | 一般 library package；繼承 workspace version/edition，依賴本 workspace 的 `framework-macros` |
| `crates/framework/src/lib.rs` | library root；此階段不公開 DI 或 framework API |
| `crates/framework-macros/Cargo.toml` | macro package；設 `[lib] proc-macro = true`，繼承 workspace version/edition |
| `crates/framework-macros/src/lib.rs` | proc-macro crate root；此階段不宣告任何 macro |

不建立發布用 metadata、CI、license、guide、tests、build script 或額外 package。公開發布前再定 package 名稱、license、README/repository metadata 與 CI 支援範圍；若發布 crates.io，`framework` 對 `framework-macros` 的 path dependency 須加上相容的 registry version requirement。

## 6. 本階段的資料流、介面與錯誤處理

本階段只確立 crate 依賴方向。`framework` 是未來一般 consumer 依賴的 facade；`framework-macros` 是編譯期語法轉換 package。Runtime traits、provider graph、bundle、capability metadata、generated code 都留到後續設計，不在 workspace 文件中定義。原始需求已將 `Register<T>` 與 `Lifecycle` 列為 framework capability 候選介面（[第 402–428 行](01-01.raw-framework-requirement.md#L402)、[第 1,328–1,364 行](01-01.raw-framework-requirement.md#L1328)），但 workspace 初始化不需先凍結其簽名。

Workspace 初始化期間的錯誤由 Cargo manifest、package name/path、dependency graph 驗證。未來 macro 對使用者輸入的錯誤應在 macro 設計階段規定成 compiler diagnostic；不在此階段增加 build script、runtime registry 或自訂錯誤框架。這也符合需求排除以 runtime `TypeId`/`Any` container 作為主要 DI resolution（[第 122–136 行](01-01.raw-framework-requirement.md#L122-L136)）。

測試策略分兩個階段：

1. **Workspace skeleton 驗收：** `cargo metadata --no-deps` 確認正好列出兩個 members；在 stable 執行 `cargo check --workspace`、`cargo test --workspace` 與 `cargo fmt --all -- --check`；檢查 target 目錄受 gitignore 覆蓋。此階段不新增測試檔。
2. **Framework 功能實作後：** 在 framework package 測 runtime behavior；macro 的 graph/metadata 純邏輯先做 unit tests，再用 consumer integration tests 驗證 compile-pass 與 compile-fail 診斷。可屆時評估 `trybuild`，現在不加入測試依賴。Example guide 後續作為文件化 consumer，不取代 framework 自身測試。

## 7. 取捨、限制與擴充

- 兩個 package 足以表達目前已確定的 runtime library / proc-macro 邊界，不先拆 graph-core 或引入第三方架構。
- 跨 crate provider/capability metadata 的表示與傳遞是 macro 功能開發的設計 gate；workspace 只預留 package 邊界，不預設解法。
- 不承諾舊 Rust compiler 支援範圍；MSRV 待公開 API、依賴版本和 CI 定稿後再宣告。
- 不承諾 `no_std`、embedded、wasm 或特定 OS 支援。若使用情境要求其中之一，需在選 dependency、async runtime 或公開 API 前補上 target matrix。
- 未來加入獨立 example guide consumer package，只依賴 `framework` facade；若 graph metadata 演進後形成清楚的純資料演算法邊界，再考慮抽成一般 Rust crate。

## 8. 具體初始化步驟

1. 在 repo root 建立 virtual `Cargo.toml`，設定兩個 members、resolver 3 和共同 version/edition。
2. 建立 `crates/framework` 一般 library package，設定對 `framework-macros` 的 path dependency。
3. 建立 `crates/framework-macros`，標記為 `proc-macro` library，不加入 macro API 或第三方依賴。
4. 加入 `rust-toolchain.toml`，選 stable、rustfmt、clippy；在 `.gitignore` 保留既有內容並新增 `/target/`。
5. 以 Cargo metadata/check 產生並檢查 `Cargo.lock`；確認 workspace skeleton 的驗收條件。

## 9. 可驗收標準

- 根目錄是一個 virtual Cargo workspace，members 僅為 `framework` 與 `framework-macros`。
- `framework` 是一般 library；`framework-macros` 是獨立 proc-macro library，依賴方向沒有循環。
- 兩個 package 共用 Rust 2024 edition；開發 toolchain 使用 stable channel。MSRV 尚未宣告。
- `Cargo.lock` 納入 repo，`/target/` 被忽略，既有 `.gitignore` 規則保留。
- 初始化不含 DI API、macro 實作、guide、測試程式碼或額外 core package。
- 驗收命令：`cargo metadata --no-deps`、stable 下的 `cargo check --workspace`、`cargo test --workspace`、`cargo fmt --all -- --check`。
