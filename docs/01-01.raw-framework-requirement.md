# Rust Compile-time DI 與 Framework Composition 需求文件

## 1. 目標

設計一套以 Rust 為核心語義的 DI 與 framework composition 機制，主要使用情境為：

* common library 提供共用 application template
* common library 提供：

  * 基礎 dependency
  * framework-managed component
  * lifecycle hooks
  * runtime registration 行為
* application 使用 common template
* application 可以：

  * 提供自己的 dependency
  * 加入自己的 component
  * 加入 lifecycle hooks
  * 對 framework runtime registry 做 extension / override
* common library 中某些具備 lifecycle / register 能力的 component，只有在 dependency graph 中實際被使用時才啟用
* DI graph 主要於 compile time 決定
* runtime framework configuration 仍允許動態邏輯

整體目標不是建立一個 runtime service locator，而是：

> 在 compile time 決定 object dependency graph，在 runtime 執行 framework configuration 與 lifecycle。

---

# 2. 核心設計原則

系統分成兩個主要層級：

```text
Compile-time DI
        ↓
Runtime Framework
```

Compile-time DI 負責：

```text
哪些 object 存在
如何 construct
dependency 關係
哪些 object reachable
```

Runtime Framework 負責：

```text
這些 object 如何設定 framework state
如何 register
如何 override runtime registry
如何執行 lifecycle
```

兩者需要明確解耦。

---

# 3. DI 基本模型

DI 的核心 abstraction 為：

```text
Provider
```

Provider 表示：

```text
Deps -> T
```

例如：

```rust
#[provide]
fn database(
    config: &Config,
) -> Arc<Database> {
    Arc::new(Database::new(config))
}
```

dependency graph：

```text
Config
  ↓
Database
```

DI framework 根據 provider function signature 建立 dependency graph。

---

# 4. Compile-time DI

DI graph 預期於 compile time 建立。

主要透過 procedural macro 產生 wiring code。

預期流程：

```text
collect provider metadata
        ↓
collect root hooks
        ↓
resolve dependency graph
        ↓
detect errors
        ↓
calculate reachable providers
        ↓
generate Rust construction code
```

runtime 不應依賴：

```rust
HashMap<TypeId, Box<dyn Any>>
```

作為主要 dependency resolution 機制。

也不以：

```rust
container.resolve::<T>()
```

作為主要使用模式。

最終 generated code 概念上接近：

```rust
let config = provide_config();
let database = provide_database(&config);
let users = provide_users(database.clone());

...
```

---

# 5. Provider

Provider 是 DI graph 的基本單位。

Provider 可以是 function：

```rust
#[provide]
fn database(...) -> Arc<Database>
```

也可以考慮支援 struct constructor 型態：

```rust
#[provide]
struct UserComponent {
    service: Arc<UserService>,
}
```

概念上等價於：

```rust
fn provide_user_component(
    service: Arc<UserService>,
) -> UserComponent {
    UserComponent { service }
}
```

因此所有 dependency 在 DI engine 看來皆為：

```text
Provider<T>
```

而不是另外建立一套 Module graph。

---

# 6. Module 的目前定義

目前認知中不需要獨立的：

```rust
#[module]
```

DI primitive。

所謂「module」本質上只是：

> 一個被 DI provide 出來，而且額外實作 framework capability 的 component。

例如：

```rust
#[provide]
struct UserModule {
    service: Arc<UserService>,
}
```

它在 DI 層只是：

```text
UserService
    ↓
UserModule
```

但它可以額外：

```rust
impl Register<Router> for UserModule
```

或：

```rust
impl Lifecycle for UserModule
```

因此：

```text
module = provided component + framework capabilities
```

而不是：

```text
module = 獨立於 provider 的 DI primitive
```

是否最後仍保留 `#[module]` 作為語法糖，可以另外評估，但目前沒有必要將其作為核心 abstraction。

---

# 7. Hook

明確宣告的 lifecycle hook 本身就是 dependency graph root。

例如：

```rust
#[hook(start)]
async fn serve(
    server: Arc<HttpServer>,
) -> Result<()> {
    server.run().await
}
```

其 graph：

```text
serve
  ↓
HttpServer
  ↓
Router
  ↓
...
```

規則：

> explicit hook 一旦被 application composition 引入，就一定是 root。

因此 hook 的 dependencies 都必須被 resolve。

---

# 8. Explicit Hook 與 Component Lifecycle 的差異

兩者不可混淆。

## Explicit Hook

例如：

```rust
#[hook(start)]
async fn serve(...)
```

語義：

```text
存在即為 root
```

它會主動把 dependency 拉入 graph。

---

## Component Lifecycle

例如：

```rust
impl Lifecycle for MetricsModule {
    ...
}
```

語義：

```text
MetricsModule reachable
        ↓
執行 Lifecycle
```

Lifecycle 本身不會讓：

```text
MetricsModule
```

成為 root。

例如：

```text
MetricsModule unreachable
```

則：

```text
不 construct
不 start
不 shutdown
```

因此：

```text
explicit hook = graph root

Lifecycle implementation
    = reachable provided component 的 capability
```

---

# 9. Reachability

application 不需要 instantiate 所有已知 provider。

從所有 explicit root hook 開始進行 graph traversal。

例如：

```text
serve
 ↓
HttpServer
 ↓
Api
 ↓
Database
```

只有 reachable provider 需要被 construct。

若存在：

```text
MetricsModule
```

但 graph 中沒有任何 path 到它：

```text
MetricsModule unreachable
```

則：

```text
不 construct MetricsModule
不執行 MetricsModule register
不執行 MetricsModule lifecycle
```

這是 framework 的重要需求。

---

# 10. Register capability

framework-managed component 可以實作 runtime registration。

基本形式：

```rust
trait Register<T> {
    fn register(&self, target: &mut T);
}
```

例如：

```rust
impl Register<Router> for UserModule {
    fn register(&self, router: &mut Router) {
        router.route(...);
    }
}
```

Register 的語義為：

> 已經被 DI construct 出來的 component，對 framework runtime state 進行 configuration。

Register 不屬於 DI registration。

---

# 11. Register 不是 Root

`Register<T>` implementation 本身不會讓 component 變成 reachable。

例如：

```rust
impl Register<Router> for HealthModule
```

但：

```text
HealthModule unreachable
```

則：

```text
HealthModule 不 construct
HealthModule::register 不執行
```

只有 dependency graph 已經需要 `HealthModule` 時，framework 才會執行：

```rust
health_module.register(&mut router);
```

---

# 12. Runtime Override

以下行為：

```rust
fn register(&self, router: &mut Router) {
    router.override(...);
}
```

屬於：

> runtime framework configuration

而不是 compile-time DI override。

例如：

```rust
impl Register<Router> for AppRoutes {
    fn register(&self, router: &mut Router) {
        router.override("/users", custom_handler);
    }
}
```

此時：

```text
AppRoutes 已經由 DI 決定存在
        ↓
runtime register
        ↓
Router runtime state 被修改
```

DI framework 不需要理解：

```rust
router.override(...)
```

的 semantics。

這完全屬於 Router / framework registry 本身。

---

# 13. Compile-time DI 與 Runtime Override 的界線

需要明確區分兩類 override。

## Framework runtime override

例如：

```rust
router.override(...)
registry.override(...)
```

發生於：

```text
Register phase
```

可以根據 runtime condition 決定：

```rust
if config.enable_new_api {
    router.override(...);
}
```

這是允許的。

---

## DI provider override

例如：

```text
原本 FooProvider -> Foo
改成 AppFooProvider -> Foo
```

會直接改變 dependency graph。

這屬於另外一個 compile-time composition feature。

目前不是第一版核心需求。

第一版優先以 runtime `Register<T>` extension / override 解決 framework extension。

---

# 14. Framework Configuration Phase

Runtime 大致需要以下 phase：

```text
construct reachable dependencies
        ↓
construct reachable framework components
        ↓
registration/configuration phase
        ↓
finalize framework state
        ↓
lifecycle start
        ↓
application running
        ↓
lifecycle shutdown
```

例如 Router：

```text
Router / RouterBuilder
      ↑
A.register(...)
B.register(...)
C.register(...)
      ↓
final runtime router
```

---

# 15. Mutable Framework State

像：

```rust
fn register(&self, router: &mut Router)
```

這種 mutable target 屬於 framework build/configuration state。

可評估是否拆成：

```rust
RouterBuilder
```

與：

```rust
Router
```

例如：

```rust
impl Register<RouterBuilder> for UserModule {
    fn register(&self, router: &mut RouterBuilder) {
        ...
    }
}
```

然後：

```rust
let router = router_builder.build();
```

這樣可以更清楚區分：

```text
mutable configuration phase
vs
runtime immutable/shared value
```

但這屬於 framework-specific API，可依不同 framework target 決定。

---

# 16. Registration Ordering

因為 runtime 可以：

```rust
router.override(...)
```

所以 register 執行順序會影響結果。

例如：

```text
CommonRoutes.register()
AppRoutes.register()
```

允許：

```text
AppRoutes
```

覆蓋 common behavior。

但：

```text
AppRoutes.register()
CommonRoutes.register()
```

可能得到不同結果。

因此 framework 必須提供 deterministic registration ordering。

目前候選規則：

```text
dependency order
+
composition order
```

common template 先，application extension 後。

例如：

```text
Common
  ↓
Application
```

register：

```text
Common registrations
        ↓
Application registrations
```

因此 app 可以自然 override common behavior。

第一版不優先考慮：

```text
priority = 100
order = -10
```

之類的 priority system。

---

# 17. Lifecycle

framework-managed provided component 可以實作 lifecycle。

初步 interface：

```rust
trait Lifecycle {
    async fn start(&self) -> Result<()> {
        Ok(())
    }

    async fn shutdown(&self) -> Result<()> {
        Ok(())
    }
}
```

語義：

```text
component reachable
        ↓
construct
        ↓
Lifecycle::start
```

shutdown：

```text
Lifecycle::shutdown
```

只針對實際 reachable component。

---

# 18. Lifecycle Ordering

Lifecycle ordering 預期應與 dependency graph 一致。

假設：

```text
HttpModule
    ↓
DatabaseModule
```

則 startup：

```text
DatabaseModule.start
HttpModule.start
```

shutdown：

```text
HttpModule.shutdown
DatabaseModule.shutdown
```

也就是：

```text
startup
    dependency topological order

shutdown
    reverse dependency order
```

這需要在實際 implementation design 階段再驗證。

---

# 19. Ownership Model

DI framework 不應自行發明新的 ownership abstraction。

直接使用 Rust type：

```rust
T
&T
&mut T
Arc<T>
Rc<T>
Box<T>
Arc<dyn Trait>
```

例如：

```rust
#[provide]
fn database(
    config: &Config,
) -> Arc<Database>
```

consumer：

```rust
fn user_service(
    db: Arc<Database>,
) -> UserService
```

macro 產生：

```rust
let service = user_service(db.clone());
```

因此：

> ownership semantics 主要由 provider / consumer 的 Rust type signature 決定。

不同 dependency 可以混用：

```text
Config       -> &Config
Database     -> Arc<Database>
Parser       -> Rc<Parser>
Foo          -> Box<Foo>
Logger       -> Arc<dyn Logger>
```

---

# 20. Ownership 限制

需要特別注意 provider output 長期持有其他 provider borrow 的情況。

例如：

```rust
fn service<'a>(
    config: &'a Config,
) -> Service<'a>
```

如果 generated application 同時保存：

```rust
struct App {
    config: Config,
    service: Service<'_>,
}
```

可能形成 self-referential struct 問題。

因此第一版可限制：

> provider 可以在 construction 過程中 borrow dependency，但 provider output 不應長期 borrow framework-owned dependency。

例如：

```rust
fn database(
    config: &Config,
) -> Database
```

可以。

但：

```rust
fn service<'a>(
    config: &'a Config,
) -> Service<'a>
```

第一版可不支援。

---

# 21. Rust Compiler 負責的 Ownership 驗證

framework 應盡量讓 Rust compiler 自己處理：

```text
Send
Sync
lifetime
ownership
borrow checking
```

例如：

```rust
Rc<T>
```

如果最後進入要求：

```rust
Send
```

的 async runtime：

```text
future cannot be sent between threads safely
```

應直接由 Rust compiler 回報。

framework 不重新實作 Rust type system。

---

# 22. Common Application Template

common library 需要可以提供 reusable composition。

概念上：

```text
Common Template
├── providers
├── framework components
├── hooks
└── framework defaults
```

application 可以在其上增加：

```text
App
├── Common Template
├── application providers
├── application components
├── application hooks
└── runtime registrations / overrides
```

目前可使用類似：

```rust
#[bundle(...)]
```

作為 reusable compile-time composition abstraction。

名稱尚未定案。

---

# 23. Application

final application 需要一個 top-level compile-time composition entry。

例如概念：

```rust
#[application(
    imports(
        CommonApp,
        MyFeature,
    )
)]
struct App;
```

application macro 負責：

```text
flatten imports
collect providers
collect hooks
build graph
check graph
generate wiring
```

實際 macro syntax 尚未定案。

---

# 24. Bundle / Composition Unit

由於 `module` 已經被理解為 runtime provided component 的 domain 概念，不建議再使用 `module` 表示 compile-time provider collection。

可考慮：

```text
Bundle
ComponentSet
Feature
Package
Composition
```

例如：

```rust
#[bundle(
    providers(...),
    hooks(...),
)]
pub struct CommonWeb;
```

其功能只是：

> 將一組 compile-time provider / hook metadata 打包供 application 引用。

不需要 runtime instance。

---

# 25. Qualifier

需要支援同型別多 provider。

例如：

```rust
fn primary_db() -> Arc<Database>;
fn replica_db() -> Arc<Database>;
```

兩者 output type 相同。

因此 DI key 不能永遠只有：

```text
Type
```

需要支援：

```text
(Type, Qualifier)
```

例如：

```rust
#[qualifier]
struct Primary;

#[qualifier]
struct Replica;
```

使用：

```rust
#[provide(Primary)]
fn primary_db() -> Arc<Database>;

#[provide(Replica)]
fn replica_db() -> Arc<Database>;
```

consumer：

```rust
fn repository(
    #[inject(Primary)]
    db: Arc<Database>,
) -> Repository
```

實際 syntax 尚未定案。

---

# 26. Compile-time Error Detection

application graph generation 至少需要檢查：

## Missing dependency

```text
Foo requires Bar
但沒有 Provider<Bar>
```

compile error。

---

## Ambiguous provider

例如：

```text
Provider<Foo>
Provider<Foo>
```

但 consumer 沒 qualifier。

compile error。

---

## Circular dependency

例如：

```text
A -> B
B -> C
C -> A
```

compile error。

---

## Invalid qualifier

consumer 指定 qualifier，但不存在對應 provider。

compile error。

---

# 27. Proc Macro 的限制

Rust procedural macro 無法任意詢問 compiler：

```text
T 有沒有 implement Lifecycle？
T 有沒有 implement Register<Router>？
```

因此 capability discovery 不能依賴一般 runtime/reflection 模型。

需要有某種 compile-time metadata 讓 application macro 知道：

```text
某個 provided type 具有哪些 framework capabilities
```

可能方案包括：

```rust
#[provide(
    lifecycle,
    register(Router),
)]
struct UserModule { ... }
```

或由另外的 capability macro 產生 metadata。

例如：

```rust
#[register(Router)]
impl Register<Router> for UserModule { ... }
```

以及：

```rust
#[lifecycle]
impl Lifecycle for UserModule { ... }
```

這部分尚未定案。

核心要求是：

> capability implementation 與 compile-time discoverability 必須同時存在。

---

# 28. 不希望出現的設計

目前不傾向以下模式。

## Runtime service locator

```rust
container.resolve::<Foo>()
```

不作為主要 API。

---

## TypeId / Any 作為核心 DI graph

```rust
HashMap<TypeId, Box<dyn Any>>
```

不作為主要 dependency resolution 機制。

---

## Module 自己動態註冊 DI Provider

例如：

```rust
fn register(&self, di: &mut Container)
```

不符合 compile-time DI 方向。

DI provider 必須在 compile-time composition 階段可知。

---

## Register 即 Root

不採用。

```text
implements Register<T>
```

不代表 object 自動進 graph。

---

## Lifecycle 即 Root

不採用。

```text
implements Lifecycle
```

不代表 object 自動進 graph。

---

## Runtime framework override 與 DI override 混為一談

不採用。

以下：

```rust
router.override(...)
```

只是 framework runtime behavior。

不應讓 DI framework理解它。

# 29. 目前的核心抽象

目前可以將整套系統簡化成：

```text
                  explicit hooks
                       │
                       │ root
                       ▼
              Dependency Graph
                       │
                reachable only
                       │
                       ▼
                  Provider<T>
                       │
                       ▼
                        T
                       │
         ┌─────────────┴─────────────┐
         │                           │
         ▼                           ▼
 optional Register<R>        optional Lifecycle
         │                           │
         ▼                           ▼
 framework configuration       runtime lifecycle
```

也就是：

```text
Hook
    = graph root

Provider
    = Deps -> T

Provided component
    = normal dependency

Register<T>
    = reachable component 的 runtime configuration capability

Lifecycle
    = reachable component 的 lifecycle capability
```

這是目前最核心的模型。

# 31. Application Template 預期使用方式

概念示例：

```rust
#[provide]
fn config() -> Config {
    ...
}

#[provide]
fn database(
    config: &Config,
) -> Arc<Database> {
    ...
}

#[provide]
struct CommonRoutes {
    users: Arc<UserHandler>,
}

impl Register<Router> for CommonRoutes {
    fn register(&self, router: &mut Router) {
        router.route("/users", ...);
    }
}
```

Common template：

```rust
#[bundle(
    providers(
        config,
        database,
        CommonRoutes,
    ),
    hooks(
        ...
    ),
)]
pub struct CommonApp;
```

App extension：

```rust
#[provide]
struct AppRoutes {
    custom_users: Arc<CustomUserHandler>,
}

impl Register<Router> for AppRoutes {
    fn register(&self, router: &mut Router) {
        router.override("/users", ...);
    }
}
```

application：

```rust
#[application(
    imports(CommonApp),
    providers(
        AppRoutes,
    ),
)]
struct App;
```

runtime registration：

```text
CommonRoutes.register()
        ↓
AppRoutes.register()
        ↓
AppRoutes 可以 override common route
```

目前非第一版核心需求。


# 33. 第一版建議 Scope

第一版建議只實作足以驗證架構的能力：

```text
1. #[provide] function
2. provided struct/component
3. #[hook] root
4. compile-time dependency graph
5. reachability
6. missing / duplicate / cycle validation
7. reusable common composition
8. Register<T>
9. Lifecycle
10. deterministic registration/lifecycle ordering
11. basic qualifier
```

暫時不做：

```text
runtime container
request scope
dynamic plugins
DI provider runtime override
priority-based ordering
arbitrary reflection
complex lifetime injection
```

# 34. 核心 Design Invariants

目前整套 framework 最重要的 invariants 可以整理成以下幾條。

### Invariant 1

```text
DI graph 在 compile time 決定。
```

---

### Invariant 2

```text
Explicit hook 是 graph root。
```

---

### Invariant 3

```text
Provider 是唯一必要的 DI graph node abstraction。
```

---

### Invariant 4

```text
所謂 module/component 本質上仍然只是被 provide 的 T。
```

---

### Invariant 5

```text
Register / Lifecycle 不會讓 T 成為 root。
```

---

### Invariant 6

```text
只有 reachable T 才會被 construct，
也只有 reachable T 的 framework capability 才會執行。
```

---

### Invariant 7

```text
compile-time 決定「誰存在」；
runtime register 決定「這些東西如何改 framework state」。
```

---

### Invariant 8

```text
Router::override(...) 類型的 override
屬於 runtime framework semantics，
不是 DI semantics。
```

---

### Invariant 9

```text
Rust ownership type 本身就是 DI ownership model。
framework 不另外發明 Shared<T> / Inject<T> 等 ownership abstraction。
```

---

### Invariant 10

```text
common library 可以提供很多 capability，
但沒有被 root graph reach 到的 component 不應產生 runtime side effect。
```

# 35. 下一階段

在需求層完成後，下一階段應以一個具體 application case 驗證架構。

建議案例：

```text
Config
  ↓
Database
  ↓
UserService
  ↓
UserRoutes

Metrics
  ↓
MetricsModule

Router
  ↓
HttpServer

serve hook
```

同時包含：

```text
common template
app extension
runtime route override
optional Metrics lifecycle
Register<Router>
async lifecycle
Arc / &T 混合 ownership
```

再針對此案例設計：

```text
1. 實際 user-facing macro syntax
2. macro metadata representation
3. generated Rust code
4. dependency graph algorithm
5. capability discovery mechanism
6. register ordering
7. lifecycle ordering
```

如果這個案例可以完整展開且 generated code 符合 Rust ownership / async 規則，再進入 framework implementation。
