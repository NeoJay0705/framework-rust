# Runtime 註冊與設定設計

## 1. 需求、範圍與假設

本階段把原始需求的 `Register<T>` 接到已完成的編譯期 provider graph 與 application `run()`。`Register<T>` 表示已建構且可達的 component 對使用者提供的 framework target 做同步 runtime configuration；它不是 DI provider 註冊，也不使 component 或 target 成為 graph root。設定邏輯與 override 語義屬 target 自己，framework 只負責以確定順序呼叫註冊（[原始需求 §10–16](01-01.raw-framework-requirement.md#L402)、[§27](01-01.raw-framework-requirement.md#L1148)）。

本次包含公開 trait、明確的 provider capability 宣告、跨 crate metadata、可達性與 target 綁定、產生註冊呼叫和診斷。`run()` 的順序擴為「建構所有可達 provider → 同步註冊 → 既有 explicit hooks」；同一次 `run()` 每個可達 provider 對每個宣告的 target 註冊一次。現有 hook 仍為 graph roots，且保留其順序與 async 行為。此階段不定義具體 Router/registry、設定檔載入、通用 runtime container、自動 finalize、Lifecycle、DI provider override 或 executor。Builder 是否轉為 runtime 值由具體 framework 或 hook 處理，`Register<T>` 不假設 `T` 必須是 Builder（[原始需求 §14–15](01-01.raw-framework-requirement.md#L561)）。

## 2. 公開介面與宣告約束

`framework` facade 提供並文件化：

```rust
pub trait Register<Target> {
    fn register(&self, target: &mut Target);
}
```

Capability 明確標在既有 function／named-field／unit-struct provider 上，對應 trait implementation 由使用者照 Rust 規則另外實作，不對 `impl` 做隱含掃描：

```rust
#[provide(register(crate::Router))]
fn common_routes() -> std::sync::Arc<crate::CommonRoutes> { /* ... */ }

#[provide(qualifier = "special", register(crate::Router, qualifier = "public"))]
struct SpecialRoutes { /* fields ... */ }

// 同一 provider 要註冊多種 target 時，可重複 register(...)
#[provide(register(crate::Router), register(crate::Commands))]
struct MultiRoutes;
```

`register(Type)` 的 Type 是 `Register<Type>` 的 target，選擇 target provider 時使用既有 `(TypeKey, QualifierKey)` 語義；`register(Type, qualifier = "name")` 選定 qualified target。Provider 自身的 `qualifier` 與 target qualifier 各自獨立。每個 target 必須由現有 provider 產生、已由 explicit hook 的 graph 遍歷變成 reachable，且與 registrar 是不同 provider instance。註冊宣告不增加 graph edge 或 root；缺少、歧義、指定錯誤 qualifier、target 不可達或 target 指向自己皆為編譯期錯誤。未標註 capability 的 `Register<T>` impl 不會自動執行。

Target type 與 provider/dependency type 使用相同的明確路徑、qualifier 和跨 crate `crate::` 正規化規則；不解析 type alias、`use` alias 或 Rust 語義上的型別等價。Provider output 以一般型別實作 `Register<T>`；對完整 `std::sync::Arc<Component>`／`std::rc::Rc<Component>` output，`Component` 實作 trait。其他 wrapper 不做特殊 deref。這讓 trait 實作與 metadata 可被編譯器及 macro 分別驗證。

## 3. 架構、資料模型與跨 crate 協定

`framework` 只定義 trait，不持有 target 或 component。`framework-macros::declaration` 擴充 provider attr parser，保存按宣告順序排列的 `RegistrationCapability { target_type, target_qualifier, wrapper_name }`；在 provider 定義 module 產生 `#[doc(hidden)] pub` 註冊 wrapper，其簽名概念上是 `(&ProviderOutput, &mut Target)`。Wrapper 以 fully-qualified `framework::Register::<Target>::register` 呼叫：一般 output 傳 `value`，完整 Arc/Rc output 傳 `&**value`。因此即使該 provider 不可達，wrapper body 仍讓 rustc 檢查宣告的 trait implementation 是否存在。Trait/callable 路徑沿用目前 facade 名稱 `framework` 的限制。

Bundle 的 `framework_bundle_metadata_v1` record 新增可省略的 registrations 欄位；舊 record 沒有此欄位時視為空清單，不破壞現有 bundle forwarding。每筆 capability 保存原始 target type syntax、optional qualifier、宣告位置及含原始 `$crate` hygiene 的 wrapper callable tokens。Application composition 只對 TypeKey 做來源 `crate::` 改寫，絕不 stringify 後重建 callable path。Local provider 使用 local wrapper，imported bundle 使用轉送的 wrapper path；此協定仍為 doc-hidden internal API，不承諾跨版本穩定。既有跨 crate forwarding proof 可傳額外 target TokenTrees，隔離 probe 亦已確認 `$crate` callable 可保持有效。

`framework-macros::application` 先以既有 `graph::resolve` 建立 `GraphPlan`，再只檢查 `construction_order` 中的 registrar。註冊 target 的 key lookup 必須沿用 graph resolver 的完整 provider 集合及 qualifier matching 規則，取得 ProviderId 後檢查它是否在 `construction_order`；不得把此 lookup 加進 roots 或使 target 變 reachable。必要時在 `graph.rs` 只抽出可重用的 request lookup，並為註冊 request 加來源 slot，以維持既有 missing/ambiguous/invalid-qualifier 診斷語義。不要重做另一套型別匹配或依賴圖。

## 4. 產生的資料流、排序與 ownership

```text
explicit hooks → graph::resolve → reachable construction_order
                                  ↓
                    bind declared registration targets
                                  ↓
                   construct reachable provider values
                                  ↓
                  register reachable components
                                  ↓
                      invoke existing hooks
```

註冊順序由 `GraphPlan.construction_order` 過濾出有 capability 的 provider 決定：dependency precedence 優先；兩個可同時建構的 provider 依現有來源順序（imports 由左至右、各 bundle 宣告順序、最後 application 宣告順序）打破平手。因此獨立項目 common 在 app 前，而跨層依賴必須先滿足；同一 provider 多個 `register(...)` 依宣告順序執行。這是原始需求「dependency order + composition order」的精確規則，不加入 priority system（[原始需求 §16](01-01.raw-framework-requirement.md#L645)、[未決事項 §32.3](01-01.raw-framework-requirement.md#L1490)）。

Codegen 沿用現有 construction plan，只把會被註冊的 target 變數宣告為 `mut`，接著依上述順序產生 `registration_wrapper(&registrar_value, &mut target_value)`；所有呼叫均在 hooks 前。Target 與 registrar 必須在此階段仍可使用：若使用者的 provider construction 已將值 move、留下不相容 borrow，Rust compiler 依原生 ownership 規則報錯；使用 shared borrow 或 `Arc`/`Rc` 是常見方式。此限制需文件化，不以 runtime storage/clone 所有值掩蓋。對同一 target 的多次 `&mut` 借用逐次結束，允許後面的 app registration 覆寫前面的 common configuration。

## 5. 錯誤處理與測試

Macro 直接診斷錯誤的 `register(...)` 語法、空 qualifier、同 provider 重複宣告同一 target key、在 hook 上誤用 capability，以及 target lookup 的 missing/ambiguous/invalid qualifier、target provider 不可達與自我 target。錯誤需帶 target type/key 與 registrar 來源；local 儘量指向宣告 Span，imported metadata Span 不可靠時列出 bundle import path。`Register<T>` impl 缺失、Rust privacy/type、move/borrow 問題由生成 wrapper／呼叫觸發 rustc 診斷。Graph resolver 原本的錯誤優先，之後才診斷可達註冊 target；不以執行期 panic 代替。

沿用現有兩 bundle crates、consumer 與獨立 compile-fail fixture；只加本階段必要案例。正向測試驗證：common/app 對同一 target 的順序與後者 override、dependency precedence、只有 reachable registrar 註冊、target 本身沒有被註冊宣告拉成 root、Arc/Rc component trait 呼叫、qualified target、零能力的舊 bundle metadata 仍可 composition、所有 registration 在 hooks 前。負向案例驗證：缺少 trait impl（含 unreachable provider 的 wrapper）、缺少/歧義/錯誤 qualifier 的 target、target 不可達、自我 target、重複 capability、錯誤語法；可以只匹配穩定診斷關鍵字，不固定完整 stderr。保持原有 graph、provider、hook 測試通過。

驗收命令：`cargo fmt --all -- --check`、`cargo check --workspace`、`cargo check --workspace --all-features`、`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、`git diff --check`。獨立 compile-fail fixture 的格式檢查沿用既有測試流程。

## 6. 取捨、限制與實作步驟

明確 `#[provide(register(...))]` 同時提供跨 crate discoverability，並透過 wrapper 編譯檢查 `Register<T>` 實作；沒有 Rust 反射或掃描任意 trait impl。註冊 target 是已可達的 provider output，沒有內建 RouterBuilder/finalize 介面；這保留 target-specific API 的自由。此階段同步、不回傳錯誤的 trait 符合原始預設；async/fallible registration、Lifecycle、通用 registry storage、DI provider override 以及更複雜 target ownership 留給後續明確需求。`run()` 仍是無參數 async API，呼叫者提供 executor。

Phase 0（已完成的技術 gate）：在 `/tmp/framework-register-metadata-probe.eG2IXw` 證明 metadata 的額外 target type 與 `$crate` callable 可跨 crate 轉送；在 `/tmp/framework-register-wrapper-probe.cRXagb` 證明一般值、Arc、Rc 的 fully-qualified trait wrapper 可執行，且 unreachable wrapper body 仍會被 rustc trait-check。這是隔離 proof，正式 repo fixtures 仍需驗證真實 macro。

Phase 1：最小修改 `crates/framework/src/lib.rs` 加文件化 `Register<T>`；擴充 `declaration.rs` 的 provider syntax、wrapper 與 optional metadata，沿用 `bundle.rs` 現有 forwarding；先以單 bundle compile-pass、缺 trait impl compile-fail 驗證定義端 gate。不得改變既有 provider/hook 語義。

Phase 2：擴充 `application.rs` 的 capability record parsing、TypeKey rewrite、可達 target lookup、registration codegen；`graph.rs` 只做必要 lookup/slot 的 crate-private 重用。驗證零、一、多 imports 不退化，並在兩個不同 crate bundles 加 app extension 上實際執行與觀察順序。

Phase 3：在既有正向及負向 fixtures 中增加 §5 案例，跑所有驗收命令；如編譯器證明 ownership 或 macro protocol 與設計矛盾，先回報具體證據再由 root 最小修訂設計。實作檔案以 `framework/src/lib.rs`、`framework-macros/src/{declaration,bundle,application,graph}.rs` 和既有 fixture 為界；只有必要時更新 manifests/lockfiles。不新增 runtime container、example guide、release metadata。
