# 編譯期依賴圖 Resolver 設計

## 1. 需求與假設

本階段只完成 `framework-macros` crate 內部的純 graph resolver。原始需求將 graph 放在 compile time 建立，流程包含收集 provider metadata、收集 root hooks、解析依賴、檢查錯誤、計算可達 providers，最後產生 Rust construction code（[原始需求 §4，第 100–119 行](01-01.raw-framework-requirement.md#L100-L119)）。此階段只實作並以私有單元測試驗證 resolver；不新增 Cargo crate、framework facade API、proc-macro entrypoint、parser、codegen、example guide 或外部依賴。

Resolver 是未來 macro 呼叫的內部純邏輯，不宣稱已完成 macro 前端、跨 crate composition、ownership wiring 或 runtime framework 行為。Provider 以 `Deps -> T` 表示（[原始需求第 71–96 行](01-01.raw-framework-requirement.md#L71-L96)）；explicit hook 是 root，graph traversal 只涵蓋 reachable providers（[原始需求第 251–280、358–398 行](01-01.raw-framework-requirement.md#L251-L280)）。

## 2. 架構邊界與選型理由

```text
frontend
   ↓ normalized descriptors
private graph resolver
   ↓ GraphPlan | GraphError
future codegen
```

本階段 resolver 放在 `framework-macros` crate 的私有 `graph` 模組，不新增 crate，也不提供 public exports。此選擇沿用原始需求以 procedural macro 建立 compile-time graph 並產生 wiring 的方向（[原始需求第 100–119 行](01-01.raw-framework-requirement.md#L100-L119)），同時讓尚無 macro entrypoint 的 graph 邏輯能由 crate 內單元測試驗證。

Frontend 後續負責 Rust syntax、跨 crate metadata、TypeKey／QualifierKey identity normalization，以及重複 hook import 判斷。Resolver 只處理正規化 descriptors 與 graph。Resolver 不碰 `TokenStream`／`Span`、Rust AST、ownership 或 `Arc` clone，也不處理 runtime `Register`／`Lifecycle`。Codegen、diagnostic、metadata 與 runtime 行為均留待後續設計；原始需求也指出 proc macro 需另有 capability compile-time metadata（[原始需求 §27，第 1148–1195 行](01-01.raw-framework-requirement.md#L1148-L1195)）。

## 3. 輸入模型與輸出

- `ProviderDescriptor` 按 composition／declaration order 傳入，含唯一 `ProviderId`、已正規化的 output key，以及有序 dependency requests。`ProviderId` 可直接使用 provider 陣列索引。
- Output key 為 `TypeKey + optional QualifierKey`。`TypeKey` 和 `QualifierKey` 是 opaque、已正規化的值；本階段只做 equality，可用內部字串儲存，不解析 Rust type 或 alias。
- `RootDescriptor` 含有序 dependency requests；roots 的順序就是 hook composition order。Request 保留其 provider dependency slot 或 root dependency slot，以便輸出 bindings 與錯誤定位到輸入位置。
- `GraphPlan` 含 reachable providers 的穩定 dependency-first construction order，以及每個 reachable provider/root request slot 對應的 `ProviderId` binding。重複 request 各自保留 binding slot，但同一 provider 只出現在 construction order 一次。Plan 不含 runtime instances。

Qualifier 是 key 的一部分，符合原始需求的 `(Type, Qualifier)` 概念（[原始需求 §25，第 1038–1092 行](01-01.raw-framework-requirement.md#L1038-L1092)）。

## 4. Resolver 流程與匹配規則

1. 依 provider declaration order 全域檢查完整 key 重複；即使重複 provider 不可達也報錯。全域重複錯誤優先於 roots 空集合的處理。
2. 若無完整 key 重複，且 roots 為空或 roots 沒有 dependency requests，回傳空 `GraphPlan`。
3. 從 roots 依宣告順序，按 root dependency slot 順序做 depth-first traversal；每個 provider 依其 dependency slot 順序遞迴解析。只解析 root dependencies 的 reachable closure，不可達 provider 的 missing、ambiguous、invalid qualifier 或 cycle 不報。
4. 首次解析到 provider 時記錄其 dependencies 與 binding；後續相同 request 仍記錄其 request slot binding，但不重複解析／建立 provider。

Provider matching 規則：

- 有 qualifier 的 request 只匹配完全相同的 `(TypeKey, QualifierKey)`。
- 無 qualifier 的 request 在相同 `TypeKey` 的所有 providers 中選唯一候選；若唯一候選本身有 qualifier，仍可匹配。
- 無 qualifier request 沒有候選時回報 `Missing`；有多個候選時回報 `Ambiguous`。
- 有 qualifier request 找不到 exact key，且該 `TypeKey` 尚無任何 provider 時回報 `Missing`；若該 type 有其他 qualifier/provider，回報 `InvalidQualifier`。
- 不同 qualifier 的同型別 providers 不算 duplicate。DI provider override 不支援。

上述 missing、ambiguous、cycle 與 invalid qualifier 均對應原始需求列出的 compile-time graph errors（[原始需求 §26，第 1096–1144 行](01-01.raw-framework-requirement.md#L1096-L1144)）。Register／Lifecycle implementation 不構成 root；只有 explicit hooks 構成 roots（[原始需求第 284–354、432–459 行](01-01.raw-framework-requirement.md#L284-L354)）。

## 5. 穩定順序與錯誤介面

Resolver 回傳 `Result<GraphPlan, GraphError>`，且只回報第一個錯誤：

- `DuplicateProvider(key, provider_ids)`：按 provider declaration order 掃描；第一個出現第二次的完整 key 為回報 group，回報該 key 的所有 `ProviderId`，依 declaration order 排列。
- `Missing(request, requester/root_slot)`
- `Ambiguous(request, candidate_ids, requester)`
- `InvalidQualifier(request, available_candidates, requester)`
- `Cycle(closed_path)`：由 `ProviderId` 組成、首尾相同且每一段都是 graph edge 的閉合路徑。

Resolution errors 按第 4 節的 root／dependency slot depth-first 順序，遇到第一個就回傳；DFS 遇到目前仍在 traversal stack 的 provider 時立即回傳該閉合 cycle。錯誤中所有 ID／candidate／path 的排列均穩定。Resolver 不產生 `compile_error!`、tokens、spans 或使用者訊息；未來 frontend 依 request slot/source origin 加上 Span 並映射成 compiler diagnostic。

Cycle 是 compile error（[原始需求第 1126–1136 行](01-01.raw-framework-requirement.md#L1126-L1136)）。Registration ordering 的需求包含 deterministic ordering 與 dependency/composition order（[原始需求第 645–707 行](01-01.raw-framework-requirement.md#L645-L707)）；本 resolver 對 construction order 的具體規則如下。

對 reachable DAG 做 topological sort；每一步從目前 indegree 為 0 的 provider 中選 declaration index 最小者。相同輸入必得相同 order。Cycle 偵測不限定其他演算法；topological construction order 不包含 runtime registration／lifecycle 執行。

## 6. 測試與驗收案例

以 `framework-macros` 私有單元測試驗證純 resolver，至少涵蓋：

1. `Config -> Database -> Service` 的 root chain 及 dependency-first construction order。
2. 兩個 roots 與重複 requests：provider 只列一次，所有 request slots 均有 binding。
3. 不可達 provider 不列入 plan；其 broken dependency 被忽略；但同完整 key 的 duplicate 即使不可達仍報錯。
4. Qualified exact match、唯一 qualified provider 滿足 unqualified request、兩個候選造成 ambiguous、qualifier 不存在時區分 invalid qualifier 與 missing。
5. Cycle 回報可驗證的閉合 ProviderId path。
6. 無 roots 或 roots 無 dependencies 時回傳空 plan（前提是全域 duplicate 檢查通過）。
7. declaration permutation 依各自 declaration index 驗證穩定 tie-break；同一輸入重複解析得到相同 plan/error。

此階段不做 macro integration 或 compile-fail tests，因為沒有 proc-macro entrypoint。

## 7. 取捨、限制與後續 gate

Resolver 只以正規化 key 做 equality；Rust type identities、borrow/reference 與 ownership wrappers 的語義不由它決定。Ownership 仍需符合 Rust type signature 的規則，原始需求明列 `T`、`&T`、`Arc<T>` 等 ownership forms，並要求由 Rust compiler 驗證 borrow／lifetime 等（[原始需求 §19–21，第 798–934 行](01-01.raw-framework-requirement.md#L798-L934)）。

進入 frontend／跨 crate 功能前需完成下列設計 gate：

- 證明 common crate 到 application crate 的 provider／hook／qualifier／capability metadata 可在 compile time 取得；原始需求指出 proc macro 無法任意反射 trait implementation，且 metadata 方式尚未定案（[原始需求 §27、§32.2，第 1148–1195、1475–1486 行](01-01.raw-framework-requirement.md#L1148-L1195)）。
- 定義 `TypeKey` identity 對 `T`、`&T`、`Arc<T>`、aliases、generic paths、跨 crate paths 的支援規則。
- 定義 ownership wiring 與 Rust compiler checking 的互動。
- 定義 request/source origin 到 source Span 與 compiler diagnostic 的映射。

以上不阻塞私有純 resolver，也不由 resolver 解決。第一版排除 runtime `TypeId`／`Any`／container、dynamic plugin、provider override、scope 與 priority ordering；原始需求將這些列在不希望採用或暫不支援的設計範圍（[原始需求第 1213–1233、1574–1606、1610–1637 行](01-01.raw-framework-requirement.md#L1213-L1233)）。

實作階段預期只新增 `crates/framework-macros/src/graph.rs`、在 `lib.rs` 加一行 private module declaration，以及必要的 unit tests（可內嵌於 `graph.rs`）；不修改其他檔案。驗收執行 `cargo fmt --all -- --check`、`cargo check --workspace`、`cargo test --workspace`、`cargo clippy --workspace`（若 clippy 可用）。
