# 宣告組合與程式碼生成設計

## 1. 需求與範圍

本階段完成可使用的 provider、hook、bundle、application 宣告，跨 crate composition、呼叫既有私有 graph resolver、生成 constructor wiring 與 hook invocation，以及 compile-time errors。這延續原始需求的 compile-time 流程：收集 provider metadata 與 root hooks、解析 graph、檢查錯誤、計算 reachable providers，再產生 Rust construction code（[原始需求 §4，第 100–119 行](01-01.raw-framework-requirement.md#L100-L119)）。

擴充既有 `framework-macros` 和 `framework` facade。可加入 `syn` 2（`full`、`visit-mut`）、`quote` 1、`proc-macro2` 1，以及實際 compile-test 所需依賴。此階段不加入 runtime DI container、`TypeId`／`Any` resolution、framework runtime API 或 example guide。`Register`／`Lifecycle` capability 的執行屬後續 runtime 模組；本階段不提供其宣告效果。跨 crate metadata 協定需能擴充，但不預設未實作的 capability。

## 2. Package 與公開宣告介面

Consumer 只依賴 `framework` facade。Facade re-export `#[framework::bundle]`、`#[framework::application]`；並以 `#[doc(hidden)]` re-export 內部 `__compose` proc macro。`framework-macros` 保持獨立 proc-macro crate；proc-macro crate 邊界與語法轉換角色見 [01-02 workspace 設計第 36–61 行](01-02.workspace-design.md#L36)。

Bundle 宣告形式：

```rust
#[framework::bundle(name = common_bundle)]
pub mod common {
    #[provide]
    fn config() -> crate::Config { /* ... */ }

    #[provide(qualifier = "primary")]
    fn primary() -> std::sync::Arc<crate::Db> { /* ... */ }

    #[hook(start)]
    async fn bootstrap(/* ... */) { /* ... */ }
}
```

Application 宣告形式：

```rust
#[framework::application(imports(common_lib::common_bundle, other_lib::other_bundle))]
pub mod app {
    #[provide]
    fn service(/* ... */) -> crate::Service { /* ... */ }

    #[hook(start)]
    async fn serve(/* ... */) { /* ... */ }
}
```

`imports(...)` 可省略。`#[inject("primary")]` 可標記 provider/hook function 參數或 provided struct 的 named fields。Provider function 必須同步、非 generic、非 method，且有明確的非 reference return type。Provider 與 hook function 均不支援 `unsafe` 或 `extern` ABI；hook 也必須非 generic。Hook 可同步或 async，只支援 unit return，允許零參數 hook。`#[provide]` 也可標記 named-field 或 unit struct，由 macro 生成 constructor wrapper；tuple 與 generic struct 暫不支援。這些 marker attributes 由 enclosing bundle/application attribute 消費並移除，不能獨立使用。

被標註的 module 必須是 crate root 的 inline module。Bundle 內原始 provider/hook function 可為 private；macro 在定義 crate 生成 `#[doc(hidden)] pub` wrapper。跨 crate 可見的參數及結果型別仍須為 public。以上 provider、hook、bundle 概念源自原始需求的 provider 與 root 定義（[原始需求第 150–186、249–280 行](01-01.raw-framework-requirement.md#L150)）及 common/application 範例（[原始需求第 938–1034、1368–1448 行](01-01.raw-framework-requirement.md#L938)）；本節列出的 syntax 與限制為本階段定案介面。

## 3. Cross-crate metadata 與 `$crate` forwarding

`bundle` attribute 輸出原 module、generated wrappers 與以 `#[macro_export]` 宣告的 bundle macro；macro export 名稱取自 `name`。Bundle macro 攜帶 provider、hook、qualifier metadata、原始型別語法及含 `$crate` hygiene 的 wrapper callable token path，不建立 runtime bundle instance。

`application` attribute 展開成 bundle macros 的巢狀 forwarding/callback chain，支援零、一或多個 imports。各 bundle 依 composition 順序累積 metadata，最後呼叫由 framework facade 隱藏 re-export 的 `__compose` proc macro。`__compose` 解析合成 metadata、呼叫 `graph::resolve`、生成完整 application module 與 `run`。

Callable path 必須保留原始 `$crate` 的 TokenTree span/hygiene，不能 stringify 後重建。Bundle metadata 保存來源 bundle identity/import path，供 TypeKey 中 bundle 來源 `crate::...` path 改寫；wrapper callable path 與 TypeKey 分開保存。Facade 是使用者預期入口；bundle export macro 雖可用路徑引用，但標為 doc-hidden，內部協定不承諾相容性。第一版要求 framework dependency 名稱為 `framework`，不支援 crate rename。

Rust Reference 說明 `macro_rules!` 的 `#[macro_export]` 會將 macro 匯出在 crate root，並指出 `$crate` 指向定義 macro 的 crate；proc macros 以 TokenStream 消費並產生 syntax（[Rust Reference: Procedural Macros](https://doc.rust-lang.org/reference/procedural-macros.html)、[Rust Reference: Macros by Example](https://doc.rust-lang.org/reference/macros-by-example.html)、[Rust Reference: `$crate` metavariable](https://doc.rust-lang.org/reference/macros-by-example.html#macro.decl.meta.dollar-crate)）。`01-03` resolver 設計已界定純 resolver 的輸入為 normalized descriptors，resolver 不處理 TokenStream/Span（[01-03 resolver 設計第 11–28 行](01-03.graph-resolver-design.md#L11)）；跨 crate metadata 是進入 frontend 的 gate（[第 79–88 行](01-03.graph-resolver-design.md#L79)）。

## 4. TypeKey、QualifierKey 與 ownership

- Qualifier 是非空、大小寫敏感的字串 symbolic key，不是 Rust marker type；使用形式為 `#[provide(qualifier = "primary")]` 與 `#[inject("primary")]`。這對應 `(Type, Qualifier)` key（[原始需求 §25，第 1038–1092 行](01-01.raw-framework-requirement.md#L1038)；[01-03 resolver key，第 25–30 行](01-03.graph-resolver-design.md#L25)）。
- TypeKey 是正規化後的 `syn::Type` token 表示。Annotated type expressions 必須使用明確路徑：`crate::...`、`std::...`、`core::...`、`alloc::...` 或 external crate path；primitive types 也允許。
- 不解析 `use` aliases、bare custom type names、`self`／`super`、associated types，也不推導 type alias 的語義等價性。遇到無法確定的 annotated type syntax 時回報 macro error，不靜默誤配。
- Bundle 來源 type 中的 `crate::...`（包括 nested generic）在 composition 時改寫為該 import path 的 crate prefix，例如 `common_lib::...`；application 自己的 `crate::...` 保留。Wrapper callable path 與 TypeKey 分開保存。
- `&T` shared borrow dependency 的 key 是 `T`，codegen 傳 `&value`；provider output `&T` 不支援。`std::sync::Arc<T>`、`std::rc::Rc<T>` 作為完整 value key，by-value parameter 以 clone 傳入；其他 by-value `T` 直接 move，多處消費由 Rust compiler 檢查。
- 支援標準 nested generic 與 `std::sync::Arc<dyn crate::Trait>`；不特別辨認未限定的 `Arc`，也不解析 `use` alias，更不將 type alias 假裝成等價 type。Provider output wrapper type 與 dependency type 的原始 Rust syntax仍供 compiler 檢查。

Ownership 依 provider/consumer Rust signature，Rust compiler 負責 move、borrow、lifetime、trait 與 type errors（[原始需求 §19–21，第 798–934 行](01-01.raw-framework-requirement.md#L798)；[01-03 resolver 限制，第 79–88 行](01-03.graph-resolver-design.md#L79)）。

## 5. 資料流與責任

```text
bundle/application frontend
  → parsed declarations and source origins
  → imported bundle metadata + local declarations
  → normalized ProviderDescriptor / RootDescriptor and slot/span map
  → graph::resolve
  → GraphPlan | GraphError
  → codegen
  → application module with constructor wiring and run()
```

- Bundle/application frontend 解析並驗證 marker syntax、移除 marker attributes、保留原 item。Bundle frontend 產生 wrappers 和 export macro。
- Application frontend flatten imports、保留來源映射、改寫並正規化 TypeKey、依 composition order 建立 descriptors 與 request slot/span map，再呼叫既有 graph resolver。Provider 順序為 imports 的順序後接 local declarations；root order 依 hook composition order。
- Codegen 只依 `GraphPlan.bindings` 與 `construction_order` 產生 dependency-first constructor `let` calls，不重新求圖。只生成 reachable provider 的 construction。然後在 generated application module 內輸出無參數 `pub async fn run()`，依 imports 順序後 local hooks 的 composition order 逐一呼叫；async hooks 使用 `.await`。
- 不在本階段實作 Register/Lifecycle 執行。Graph resolver 的 plan/order 與純邏輯邊界見 [01-03 第 23–63 行](01-03.graph-resolver-design.md#L23)。

Application macro flatten imports、collect providers/hooks、build/check graph、generate wiring 的責任承自原始需求（[§23，第 975–1002 行](01-01.raw-framework-requirement.md#L975)）。Explicit hook 是 graph root，只有 reachable providers 會 construct（[第 251–280、358–398 行](01-01.raw-framework-requirement.md#L251)）。

## 6. Compile-time errors

Graph resolver 只回傳第一個 `GraphError`；frontend/codegen 將其轉成 `compile_error!`。診斷需指出 dependency/type/qualifier，並在適用時列出可用 candidate 或 cycle path。盡量使用本地來源 Span；跨 crate Span 不可靠時，diagnostic 指出 bundle/import path。Resolver 的第一錯誤與結構化 variants 見 [01-03 第 49–59 行](01-03.graph-resolver-design.md#L49)。

Macro 直接診斷不支援的 syntax/type syntax。若使用者 item 已有 `run` 而生成 API 也會使用該名稱，macro 必須報錯，不能靜默覆蓋。Move、borrow、trait、type 及 private cross-crate type 可見性錯誤交由 Rust compiler 回報。原始 graph errors 包含 missing、ambiguous、cycle、invalid qualifier（[原始需求 §26，第 1096–1144 行](01-01.raw-framework-requirement.md#L1096)）。

## 7. 測試策略

保留 graph unit tests。正向 consumer fixtures（兩個 bundle crates 與 consumer package）列為 root workspace members，並以 compile/run tests 覆蓋 function 與 struct providers、borrow、Arc clone、qualifier、unreachable provider exclusion、sync/async hooks、零／一／多 imports；以事件輸出驗證執行順序。

Compile-fail fixture 使用獨立 `[workspace]`，不列入 root workspace，避免 `cargo check --workspace --all-features` 啟用預期失敗的 feature cases；它有自己的 lockfile。Consumer test harness 逐一以 `cargo check --manifest-path ... --features <case>` 執行 missing、ambiguous、cycle、invalid qualifier、unsupported syntax、duplicate provider，僅驗證非零退出及穩定診斷關鍵字，不比對完整 stderr。可額外用 private cross-crate type 驗證 rustc 的可見性檢查；若 fixture 下結果不可靠，則不列為必要 gate。正向 fixture packages 使用 `publish = false`，是測試 consumers，不是未來 example guide。

驗收命令：`cargo fmt --all -- --check`、`cargo check --workspace`、`cargo check --workspace --all-features`、`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`。

## 8. 取捨、限制與後續 gate

本階段採 compile-time declaration、metadata forwarding 與 generated Rust wiring；不建立 runtime container。Macro errors 只回報 graph resolver 的第一個錯誤；後續 Rust compiler 負責 ownership/type correctness。跨 crate span 的可用性有限，診斷以 bundle/import path 補充來源資訊。

本次只解除 provider/hook/qualifier metadata 的跨 crate 傳遞 gate；capability discovery/metadata 仍是後續 Register/Lifecycle 階段的前置 gate。其他後續項目包括 Register/Lifecycle capability 執行、fallible/async providers、長期 borrow output、type aliases／`use` imports／associated types 的 identity 等價、framework crate rename、runtime hook error policies 與 executor。發布前處理 path dependency 的 registry version、README、license 與 CI；workspace 初始化文件也將發布資訊列為後續事項（[01-02 第 91、104–110 行](01-02.workspace-design.md#L91)）。

原始需求將 runtime container、dynamic plugins、DI provider override、priority ordering、arbitrary reflection、complex lifetime injection 列為第一版暫不做的項目（[原始需求 §33，第 1610–1637 行](01-01.raw-framework-requirement.md#L1610)）。Hook `run()` 是順序執行 hooks 的最小入口；不代表 runtime lifecycle、executor 或錯誤政策已完成。若 Rust expansion order 或 TokenTree 行為使跨 crate metadata forwarding 無法成立，先回報具體證據，再修訂設計。

## 9. 實作階段、變更清單與驗收

### Phase 0：既有跨 crate metadata proof 與 gate 結論

已在 `/tmp/framework-metadata-probe.PGOf8j` 完成隔離技術 proof。Attribute macro 直接處理含 inner imported macro invocation 的 item 時，無法取得該 invocation 已展開的內容；透過 app-side `macro_rules!` forwarding，兩個不同 common crates 的 metadata 與原始 `$crate` callable tokens 可傳入 proc macro，proc macro 保留 tokens 並生成呼叫，`cargo check` 與 `cargo run` 均成功。

**結論與驗收：** 此 proof 解除 provider/hook/qualifier metadata 的跨 crate 傳遞 gate；capability discovery/metadata 仍是後續 Register/Lifecycle 階段的前置 gate。此 Phase 記錄既有隔離實驗結果，不要求 macro 尚未實作前建立 repo fixture。

### Phase 1：宣告 frontend 與 bundle exporter

新增必要的 `syn`／`quote`／`proc-macro2` 及 compile-test dependencies，更新 manifests/lockfile；在 `framework-macros/src/lib.rs` 放 proc-macro entrypoints，新增 `declaration.rs` 解析與驗證 marker/type syntax、`bundle.rs` 產生原 module、wrappers 與 metadata export macro；在 `framework/src/lib.rs` re-export public bundle/application macros 與 hidden `__compose`。

**驗收：** bundle fixture compile-pass；provider function、named-field/unit struct、qualifier、inject 與 hook markers 均按宣告介面解析，markers 被消費並移除；不支援語法產生 compile error；bundle wrapper 可供跨 crate application 呼叫。

### Phase 2：Application composition 與 codegen

新增 `application.rs` 處理 imports forwarding、metadata flattening、來源/type normalization、descriptor/span maps；依 GraphPlan 呼叫 constructors 並生成 application module 的 `pub async fn run()`。沿用 `graph.rs`，只調整必要的 crate-private visibility；不重新求 graph。

**驗收：** 零、一、多 imports compile-pass；只 construct reachable providers；constructor wiring dependency-first；hooks 依 composition order 順序呼叫並 await async hook；已有 `run` 名稱時產生診斷；兩個不同 bundle crates 加 app extension 可 compile/run。

### Phase 3：Integration 與 compile-fail tests

建立並執行 `tests/fixtures/` 中兩個正向 bundle crates 與 consumer package，並將它們加入 root workspace；consumer run tests 覆蓋零、一、多 imports 與 provider/hook 執行順序。Compile-fail package 放在獨立 `[workspace]`，不加入 root workspace，並維護自己的 lockfile；consumer harness 逐 feature 以 `cargo check --manifest-path` 執行六類錯誤，驗證非零退出與穩定診斷關鍵字。這是 review 時避免 root `--all-features` gate 被負向 fixtures 破壞的必要調整。

**驗收：** 事件輸出證明 provider/hook 執行次序；compile-fail harness 對上述錯誤收到非零退出與預期診斷關鍵字；五個驗收命令全數通過。Harness 不依賴完整 stderr snapshot。

實作檔案邊界為 `framework-macros/src/lib.rs`、新增 `declaration.rs`、`bundle.rs`、`application.rs`，沿用並僅調整 `graph.rs` crate-private visibility；`framework/src/lib.rs` facade re-exports；更新必要的 manifests 與 lockfiles；root `Cargo.toml` 僅在需要時加入 `tests/fixtures` workspace members。不新增 framework runtime API、guide 或發布 metadata。
