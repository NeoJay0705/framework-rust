# 七種組合用法示範設計

## 1. 需求、假設與範圍

本階段交付可執行、可閱讀的 example guide，逐一展示使用者前一輪確認的七種組合：未匯入 bundle；已匯入但 provider 不可達；已匯入且明確宣告 hook；應用 hook 注入服務並帶出跨 bundle 的間接依賴；可達 provider 同時註冊與參與 Lifecycle；同一 bundle 只選用部分 provider；以及啟動失敗時的回滾。這些示範應讓讀者從宣告、組合、執行順序與輸出看到實際效果，而非只閱讀測試 fixture。原始需求 §35 的 common template、app extension、route override、optional Metrics、`Register<Router>`、async lifecycle、`Arc`／`&T` ownership 也在上述案例中各有對應，不另增加第八種案例。

語意依既有 `01-03` 至 `01-06` 設計與現有公開 API：`#[hook(start)]` 是 explicit root，匯入該 bundle 就會執行，並使其注入的 provider 可達；`#[provide(lifecycle)]` 或 `register(...)` 只作用於可達 provider，單純實作 trait 不產生 root。未匯入的 bundle 完全不參與組合。示範不得為迎合情境而修改框架語意或新增條件式 hook API。`run()` 是一次性啟動／關閉入口；持續運行使用 `run_until(stop)`，受控停止後反向逐一 await shutdown。

## 2. 專案組織與技術選擇

新增一個 workspace example package `examples/composition-guide`，package 名 `composition-guide`，依賴現有 path `framework`。在該 package 的 library 定義可重用的基礎 bundle、示例型別與只供示範使用的事件記錄；在 `src/bin/` 放七個名稱能對應情境的獨立 binary。每個 binary 自行宣告 `#[application]` 與必要的本地擴充，使用 `cargo run -p composition-guide --bin <name>` 可單獨執行。`examples/composition-guide/README.md` 提供七個命令、各自重點、預期順序與入口連結，並說明 explicit hook 和 reachable capability 的差別。根 workspace manifest 只增加這個 member；Cargo.lock 若因新 workspace member 更新，保留其正常產物。不改框架 crate、舊 fixture 與既有設計文件。

共用支援碼使用標準函式庫記錄並輸出有序事件，及一個只供 examples 使用的最小 future executor。需要展示 `run_until` 的案例以標準函式庫的一次性停止訊號與執行緒，在啟動 hook 完成後發出 stop；該支援碼放在 example package，不成為 framework API。避免引入 Tokio 或其他 runtime 依賴，只為示範增添外部依賴。所有元件只模擬設定、路由、資料庫和服務的生命周期／註冊，不啟動真實網路服務，避免環境依賴與隱藏副作用。

## 3. 七個 binary 的驗收契約

| Binary | 情境與可觀察重點 |
| --- | --- |
| `unimported_bundle` | 基礎 bundle 已在 library 宣告，但應用不 import；只執行本地 explicit hook，不出現基礎 bundle 事件。 |
| `unused_import` | import 無 explicit hook 的 Metrics bundle；app hook 不注入 Metrics；不建構、不啟動、不關閉 Metrics。 |
| `explicit_hook` | import 有 explicit hook 的基礎 bundle；即使 app hook 不直接注入該 bundle 型別，基礎 hook 仍執行，且其參數所需 provider 會建構。 |
| `transitive_lifecycle` | app hook 注入 Server，Server provider 間接依賴另一 bundle 的 Database；Database 先啟動，Server 後啟動，shutdown 反序；示範 `Arc<T>` 與 `&T` 可用的依賴。 |
| `registration_lifecycle` | 可達路由提供者同時有 `Register<Router>` 與 `Lifecycle`；基礎與 app 擴充路由依確定順序註冊，app 設定成為有效路由；hook 完成後由外部 stop future 結束 `run_until`，再反向關閉。 |
| `partial_bundle` | 同一 bundle 有多個 provider，其中 qualified primary service 被 app hook 選用，alternate service 與未使用 worker 不會建構或執行 Lifecycle；示範 `#[inject("primary")]`。 |
| `startup_failure` | 可達鏈中的一個元件 start 回傳錯誤；後續元件與 hook 不啟動，僅先前成功啟動者反向 shutdown；即使 shutdown 也失敗，`RunError` 仍依順序保留 start 與 shutdown 錯誤。 |

上述每個 binary 都要在輸出中顯示足以辨識情境的事件；說明文件提供可重現命令與預期關鍵順序。使用真實 `#[bundle]`／`#[application]`／`#[provide]`／`#[hook(start)]` 宣告及 generated `run`／`run_until`，不手動模擬 framework 的依賴解析。需要被比較的事件應使用穩定字串，避免依賴時間、執行緒排程或診斷訊息全文。對於「沒有執行」的情境，整合測試應檢查輸出中不存在對應事件，而不只檢查成功退出。

## 4. 資料模型、流程與介面責任

共享 library 的示例型別代表 Config／Metrics／Database／Server／Router／RouteContributor／Service 等具體角色；bundle 定義哪些 provider 與 explicit hook 可供 app import。示例 event recorder 只觀察 constructor、registration、start、hook、shutdown 的實際執行順序；binary 的 `main` 呼叫 generated entrypoint，處理其 `Result`，再輸出 trace。正常案例若出錯應以非零退出；失敗案例則把預期 `RunError.failures()` 的 phase、component 和 source 呈現給讀者。示例 helper 不代替 framework 執行任何 graph 或 Lifecycle 邏輯。

資料流仍是 application imports → 編譯期 graph 與可達性 → provider 建構 → registration → Lifecycle start → explicit hooks → one-shot 或 stop future → reverse shutdown。示範只添加輸入宣告與可觀察輸出，不修改此順序。停止訊號範例需要等待 hook 已完成才觸發，以確保展示運行中受控停止；同步安排須可確定、不能依賴固定 sleep。`startup_failure` 使用獨立 application，故不干擾正常示範。

## 5. 錯誤、驗證與維護策略

新增 example package 的整合 smoke test，從七個 binary 真正執行生成的 application，檢查正常情境的關鍵事件順序與不應出現的事件；失敗情境檢查回滾和聚合錯誤順序。測試可使用 Cargo 提供的 binary 路徑，避免重寫示範邏輯或依賴內部 codegen 字串。執行 `cargo fmt --all -- --check`、`cargo test --workspace --offline`、`cargo clippy --workspace --all-targets -- -D warnings`，並逐一執行七個 demo 命令，核對 README 的命令可用。需要新增的 helper 僅服務 demo，保持小而直接；不得把測試用 fixtures 原封搬入 example，或為範例新增框架功能。

## 6. 決策與限制

七個 binary 對應七個情境，讀者可按需求選看；共享 library 避免重複宣告 base bundle。這比一個包含大量分支的示範程式容易查找，也不需要七個獨立 Cargo package。輸出採事件 trace 而非真實 HTTP／資料庫，可穩定驗證依賴、註冊與生命週期語意；代價是不展示特定 runtime 或網路框架整合。若將來需要真實服務的 graceful shutdown，可另加獨立 guide，不改這七個最小可執行範例。
