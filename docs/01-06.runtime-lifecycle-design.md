# Runtime 生命週期設計

## 1. 範圍與需求判讀

本階段接續 `01-03` 的編譯期依賴圖、`01-04` 的宣告組合／codegen 與 `01-05` 的同步註冊。原始需求 §14、§17、§18、§27、§33 要求：只對 reachable component 執行 `Lifecycle`，啟動依依賴拓樸順序，關閉依其反序，且 capability 須能在編譯期被宣告與發現。既有 explicit `#[hook(start)]` 仍是 graph root；Lifecycle 宣告不產生 root，也不改變依賴圖。使用者已確認：`start` 應完成啟動後返回；長時間運行的服務由 component 持有；framework 收到受控停止訊號後，逐一 await 各 component 的 `shutdown`。停止接收請求、等待 in-flight 任務等 graceful shutdown 細節由 component 實作。

合理假設：`#[hook(start)]` 是有限時間的啟動工作，位於 lifecycle start 之後、等待停止訊號之前。既有無參數 `run()` 保留為一次性入口，執行啟動 hook 後立即依序關閉；持續運行的應用使用新增 `run_until(stop)`。兩者改回傳 `Result<(), RunError>`，避免吞掉 lifecycle 錯誤；這是對 `01-04`/`01-05` 尚未處理生命週期時的 `run()` 行為所作的必要擴充。`run_until` 接受 `Future<Output = ()>`；停止訊號的建立與 executor 由呼叫者負責。

## 2. 架構、模組邊界與技術選型

`framework` facade 定義公開 `Lifecycle` trait 與執行錯誤型別；不引入 runtime、executor、signal 或 DI container。`framework-macros` 的 declaration/exporter 解析 `#[provide(lifecycle)]`，為 provider 產生定義所在 crate 的呼叫 wrapper，並把 capability 與 wrapper 路徑寫入既有 `framework_bundle_metadata_v1`。application importer 解析可選 lifecycle metadata；graph resolver 維持不變；application codegen 在既有建構與同步註冊後加入 lifecycle start、hooks、停止等待與 shutdown。

使用 stable Rust 的 trait `async fn`，允許預設空實作與不要求 `Send` 的 future；不使用 trait object 或動態掃描。因 async 清理必須被 await，受控停止是保證順序關閉的唯一途徑；外部直接 drop/abort `run_until` future 無法保證清理。

## 3. 介面、資料模型與 metadata

公開介面：

```rust
pub type LifecycleResult = Result<(), Box<dyn std::error::Error + Send + Sync>>;

pub trait Lifecycle {
    async fn start(&self) -> LifecycleResult { Ok(()) }
    async fn shutdown(&self) -> LifecycleResult { Ok(()) }
}

// 由 #[application] 在宣告模組生成
pub async fn run() -> Result<(), framework::RunError>;
pub async fn run_until<S: std::future::Future<Output = ()>>(
    stop: S,
) -> Result<(), framework::RunError>;
```

提供 `RunError`、`LifecycleFailure`、`LifecyclePhase::{Start, Shutdown}`。每筆 failure 保存 phase、component 識別字與原始 boxed error；`RunError` 依實際發生順序保存所有 failure，實作 `Display`/`Error`，並以唯讀 accessor 供呼叫者檢查。component 識別字取穩定的 provider 宣告來源／名稱，不依賴 runtime 型別反射。這些型別只表示 lifecycle 方法回傳的錯誤；provider 建構、同步註冊與 hooks 目前沒有 `Result` 契約，panic 不在本階段恢復範圍。

`#[provide(lifecycle)]` 可加在既有支援的 provider function、具名 struct、unit struct，並可與 `register(...)`、`qualifier = "..."` 合用；不另加 `#[lifecycle]` 或掃描 trait implementation。宣告端輸出 start/shutdown wrapper，對實際值使用 fully qualified `Lifecycle` 呼叫；當 provider 輸出完整 `Arc<T>`／`Rc<T>` 型別時，對 inner `T` 呼叫。沒有 `Lifecycle` impl 應在編譯時顯示 trait-bound 錯誤，即使 provider 在某個 application 中不可達。metadata 沿用 `framework_bundle_metadata_v1`，增添可選 lifecycle 記錄（flag 和兩個 wrapper callable）；舊 metadata 缺欄位視為無 lifecycle。維持現有 token 路徑／跨 crate wrapper 的衛生與可見性慣例。重複或錯誤 lifecycle 宣告應給出 span 對應的編譯錯誤。

## 4. 資料流與順序

`#[application]` 依原規則展開 imports、解析 roots 與 `GraphPlan.construction_order`。依其順序建構所有 reachable providers，再執行既有同步註冊。從 construction order 過濾有 lifecycle 的 provider 形成 `start_order`；只對這些已建構的實例呼叫 start，不對不可達 provider 呼叫。成功 start 的實例加入 started 清單；shutdown 僅對 started 清單反序、逐一 await，不能平行執行。相同 graph 與來源次序應有確定的執行順序。

成功路徑：建構 → 註冊 → lifecycle start → explicit hooks（既有順序，async hook await 完成）→ `run_until` 等待 stop／`run` 立即進入關閉 → lifecycle shutdown。`run_until` 在第一個 start 前、各 start 返回後及各 hook 前對同一個 pinned stop future 做非阻塞單次 poll；若 stop 已就緒，停止後續 start/hook 並立即反序關閉成功啟動者。進行中的 start 或 hook 不被強制中斷；方法返回後才觀察 stop。hooks 全部完成且 stop 尚未就緒時，正常 await 同一 future。此檢查不重建 stop future，也不 busy-poll。若 stop 在 startup 中被觀察到且所有 shutdown 成功，回傳 `Ok(())`。

若某個 start 回傳 `Err`，不呼叫該失敗 component 的 shutdown（它須自行清理部分啟動）；停止後續 start 與 hooks，反序 shutdown 先前成功啟動者。每個 shutdown 即使失敗，仍繼續處理剩餘 component；結果依發生順序聚合原始 start error 與 shutdown errors。正常停止時也聚合所有 shutdown errors；無錯誤才回傳 `Ok(())`。`run()` 與 `run_until` 共享同一執行語義與失敗政策，不為 one-shot 路徑複製另一套規則。

## 5. 實作順序與測試

1. 在 `framework` 加入 trait、結果別名與具來源的聚合錯誤型別；在 declaration parser/codegen 增加 `#[provide(lifecycle)]` 和定義端 wrappers，擴充 metadata 並保持舊格式相容。
2. 在 application importer/codegen 將 lifecycle capability 綁到既有 reachable construction order，生成兩個入口的共用執行流程與 stop 檢查；graph resolver 不變。檢查新生成名稱與使用者宣告的衝突。
3. 更新現有 `run()` 測試以檢查 `Result`；在既有 fixtures 驗證 direct/Arc/Rc、跨 bundle 引用、reachable 過濾、register→start→hook→stop→反序 shutdown、預先／中途就緒的 stop、等待後喚醒、startup 失敗回滾與多個 shutdown 失敗仍全部嘗試。加入有意義的 compile-fail 案例：無 trait impl、重複或不合法標記、新入口名稱衝突。若原有單次 poll 的測試 executor 無法測 pending signal，僅在測試中加最小可喚醒 executor。
4. 驗證 `cargo fmt --all -- --check`、`cargo test --workspace --offline`，以及既有 compile-fail harness；測試不能只比對生成字串，應執行實際生成的 application。

## 6. 決策、取捨與限制

採明確 capability metadata，因 proc macro 無法自動發現任意 trait impl；這也維持跨 crate 的可預期行為。沿用 graph construction order，不另建 lifecycle 排序器。`run()` 成為 one-shot 並回傳 `Result`，讓既有簡短 application 可直接檢查錯誤；需要持續運行的服務使用 `run_until`。兩者仍不自帶 executor，避免不必要的 runtime 綁定。停止後逐一 await shutdown，framework 保證的是呼叫與等待的順序；實際 grace period 由 component 決定。

本階段不做自動 OS signal、timeout、強制取消中的方法、drop/abort 時 async cleanup、錯誤後重試、額外 lifecycle phases、動態 runtime container 或隱式 root。若日後需要這些功能，應以獨立設計擴充，避免改變本階段的 deterministic ordering 與 explicit reachability 契約。
